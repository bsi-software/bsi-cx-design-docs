Confluence: Documentation Restructuring Implementation Plan

Preamble and Strategic Project Goals

Primary Objective and Rationale

The purpose of this plan is to elevate the BSI CX Design documentation (from the former technical reference at bsi-cx-docs 24.2) to a Certified, Tutorial-Based Learning Manual.

This transformation addresses two strategic objectives:

  • Accelerate onboarding and learning efficiency: Enable new CX Design team members, partners, and agencies to become self-sufficient faster, with a clear, guided learning path.

  • Unify and centralize knowledge: Merge all key resources, including materials from the GitHub Wiki, into a single, authoritative documentation hub, ensuring long-term maintainability and consistency.

This restructuring initiative also resolves the issues identified in the official tickets: #366888 (need for a simplified "Quick Start" experience) and #392620 (need to eliminate knowledge dispersion).

Detailed Analysis of Identified Issues and Adopted Solutions

Current Issue Detail and Noted Impact Resolution Strategy

Inconsistent Initial Workflow

New users struggle with the full architecture when attempting simple tasks (e.g., first build, logo change).

Section 1: Quick Start. Creation of a distinct, low-friction path for high autonomy in minimal time.

Dispersion of Critical Knowledge

Vital development information (Builder Syntax, UUID/Parts, advanced Twig Functions) is fragmented across the GitHub Wiki.

Centralization & Reorganization (Sections 2, 3, 5). Migration of all core content from the Wiki into the official documentation.

Excessive Granularity and Overlap

Previous index categorization (Architecture, Specification, Coding) was redundant and not intuitive.

Logical Merging (Section 2: Core Development). Fusion into a single, cohesive block guiding the user through structure, specification (Builder), and code integration.

Lack of Structured Practical Tutorials

Theory outweighs complete examples, hindering understanding of the element’s lifecycle.

Didactic Separation (Appendix A). All long tutorials and complex code examples are moved to a dedicated case study section.

Binding Restructuring Principles

All restructuring actions are governed by the following binding principles:

  • Content Preservation: No information is removed; all technical details (from 1.1 to 6.2.5 of the previous documentation) are retained.

  • Centralization: The official documentation becomes the single source of truth. The Wiki will only host specialized build-tool information.

  • Didactic UX Optimization: The documentation is reorganized as a guided progression:

    Context (0) → Quick Start (1) → Core Development (2) → Advanced Features (3) → Build & Architecture (4) → Maintenance (5) → Case Studies (A)

Definitive Executive Restructuring Plan (Detailed Index)

The final structure is reorganized into five main sections, a crucial Prerequisites block, and a dedicated Appendix, ensuring a logical flow and comprehensive content mapping.

Next Phases

To ensure a smooth and sustainable implementation, the restructuring will be executed in four progressive phases. Each phase is designed to deliver tangible results while maintaining content integrity and minimizing disruption to ongoing development work.

This staged approach ensures that the documentation evolves from foundation to full maturity, aligning with both technical and organizational priorities.

Phase Description Primary Deliverable

Phase 1: Quick Wins & Foundation

Develop and publish the Quick Start Guide (Section 1) and centralize Wiki content by migrating relevant materials (Sections 0.2, 2.3, 3.2, and 5.2). This phase directly addresses Tickets #366888 and #392620.

Functional Quick Start Guide and Full Wiki Content Migration.

Phase 2: Core Development Restructure

Refactor and merge existing content from Sections 2, 3, and 4 into the new cohesive architecture (Core Development and Advanced Features). Ensure consistent terminology, navigation, and internal linking.

Complete Sections 0–3 of the new manual.

Phase 3: Advanced Content & Finalization

Develop new content (Sections 3.1, 5.5) and Appendices (A.1, A.2, A.3) with end-to-end tutorials. Review and finalize Sections 4 and 5, focusing on Build, Maintenance, and Version Control.

Final Draft of the Complete Documentation (v. 24.2).

Phase 4: Review and Deployment

Conduct an internal review process (technical, linguistic, and didactic). Once validated, publish the documentation on the designated platform (e.g., Confluence, GitHub Pages, or BSI internal portal).
